# Democratizing GraphRAG: Linear, CPU-Only Graph Retrieval for Multi-Hop QA
Qizhi Wang (PingCAP, Data & AI-Innovation Lab, Beijing, China)  
qizhi.wang@pingcap.com  
arXiv:2602.23372v1 [cs.IR] 27 Dec 2025

## Abstract
GraphRAG systems improve multi-hop retrieval by modeling structure, but many approaches rely on expensive LLM-based graph construction and GPU-heavy inference. We present **SPRIG** (Seeded Propagation for Retrieval In Graphs), a CPU-only, linear-time, token-free GraphRAG pipeline that replaces LLM graph building with lightweight NER-driven co-occurrence graphs and uses Personalized PageRank (PPR) for retrieval. We evaluate on HotpotQA and 2WikiMultiHopQA with BM25, dense retrieval, reciprocal-rank fusion (RRF), and a TF–IDF PPR baseline, focusing on retrieval quality and system efficiency. We provide ablations over seed size, NER choice, and PPR parameters, plus scalability curves and end-to-end QA on a 1,000-query subset. Lightweight alias disambiguation and hub pruning reduce query time by 16–28% with negligible Recall@10 changes. The results characterize when CPU-friendly graph retrieval helps multi-hop recall and when strong lexical hybrids (RRF) are sufficient, outlining a realistic path to democratizing GraphRAG without token costs or GPU requirements.

## 1. Introduction
Retrieval-augmented generation (RAG) mitigates hallucinations by grounding LLMs in external evidence, yet dense retrieval can struggle with multi-hop reasoning where evidence spans multiple documents. Graph-based retrieval augments RAG with structured traversal, but many GraphRAG variants rely on LLMs for relation extraction or graph summarization, driving cost and hardware requirements. This limits adoption in academic and low-resource settings, where CPU-only constraints and tight memory budgets are common.

This paper studies a pragmatic question: *How far can we go with a linear-time, CPU-only GraphRAG that uses no LLMs during indexing?* We focus on a lightweight entity–document co-occurrence graph and sparse Personalized PageRank (PPR) retrieval. This setup provides a transparent baseline for “democratized” GraphRAG that can be run on commodity hardware.

**Contributions**:
1. **SPRIG**: A CPU-only, linear-time, token-free GraphRAG pipeline with NER-based co-occurrence graphs.
2. **Lightweight graph refinements** for CPU settings: (i) title-alias entity disambiguation (SPRIG-EL), (ii) hub pruning/edge caps (SPRIG-PRUNE), and (iii) explicit entity–document seed mixing (SPRIG-MIX).
3. **GraphHybrid/GraphDense variants** that improve Recall@10 over BM25 on both datasets with hub-aware normalization and rank-weighted seeding.
4. Comparisons against CPU-friendly baselines (RM3, BM25+CE reranker) and an ANN vs. exact seeding analysis.
5. Extensive efficiency curves, latency distributions, and ablations over seed size, seed weighting, hub penalty, and PPR modes.

## 2. Related Work
GraphRAG methods use graph structure to improve retrieval and reasoning. Recent work explores efficient and token-free variants (e.g., LinearRAG, HippoRAG, TERAG), but they often still assume GPU-heavy inference or richer graph construction. We position our work as a practical CPU-only instantiation focusing on retrieval evaluation under a strict 4 GB memory budget.

Baselines include:
- **Sparse**: BM25, classical pseudo-relevance feedback (RM3).
- **Dense**: Sentence-BERT variants (e.g., BAAI/bge-small-en-v1.5).
- **Reranking**: Cross-encoders (TinyBERT).
- **Graph/PPR**: MixPR, LightPAL, TextRank, LexRank, and recent CPU-friendly dense retrievers like LADR and MoPo.

## 3. Method

### 3.1 Pipeline Overview
1. Normalize text.
2. Extract entities with lightweight NER (SpaCy or regex).
3. Build an entity–document bipartite graph with TF–IDF weighting.
4. Create a seed distribution from the query (entities or top-k BM25/dense passages).
5. Run PPR by power iteration or push-based approximation.
6. Rank passages by PPR scores.

### 3.2 Graph Construction (Linear-Time)
We construct an entity–document bipartite graph. For each document passage $d$, we extract entities $e$ via lightweight NER. The regex heuristic extracts 1–4 token capitalized spans. We add weighted edges:
$$ w_{e,d} = tf(e, d) \cdot \log\left(\frac{N + 1}{df(e) + 1}\right) + 1 $$
where $N$ is the number of passages and $df(e)$ is entity document frequency. The adjacency matrix $W$ is row-normalized to obtain the transition matrix $P = D^{-1}W$.

**Refinements**:
- **SPRIG-EL**: Lightweight title-alias disambiguation by mapping normalized mentions to unambiguous document-title aliases (zero-KB, CPU-only).
- **Hub Downweighting**: Scale document→entity edges by $df(e)^{-p}$ ($p \ge 0$).
- **SPRIG-PRUNE**: Prune top-$x\%$ entities by $df$ or cap per-entity outdegree to top-$L$ TF–IDF edges.

### 3.3 Retrieval via PPR
Given a query, we run PPR with damping factor $\alpha$ for $T$ iterations:
$$ r = \alpha s + (1 - \alpha) P^\top r $$
where $s$ is the seed distribution. For **GraphHybrid/GraphDense**, we mix entity seeds ($s_e$) and passage seeds ($s_d$):
$$ s = \text{norm}(\alpha_{mix} s_e + (1 - \alpha_{mix}) s_d) $$
Default is “mass-proportional” mixing; adaptive option uses Laplace-smoothed $\alpha_{mix} = \frac{n_e + 1}{n_e + n_d + 2}$.

### 3.4 Complexity and Memory
- Graph construction: $O(M)$ where $M$ is the number of entity mentions.
- PPR query: $O(T \cdot E)$ using sparse matrix-vector multiplication.
- Memory: $O(E + V)$ for sparse adjacency and node scores. All experiments verify the 4 GB RAM constraint.

## 4. Experimental Setup
- **Datasets**: HotpotQA (7,405 queries, 66,581 passages) and 2WikiMultiHopQA (10,000 queries, 45,902 passages).
- **Metrics**: Recall@K, Hit@K, MRR, and end-to-end QA (DistilBERT QA on 1,000-query subsets).
- **Baselines**: BM25, BM25+RM3, BM25-2step, Dense (bge-small), RRF, BM25+CE (TinyBERT), TF–IDF Graph PPR, Graph, GraphHybrid, GraphDense.
- **Settings**: PPR $\alpha=0.15$, max iter=5. Seed sizes: $k=5$ (GraphDense) and $k=10$ (GraphHybrid) for HotpotQA; $k=3$ and $k=5$ for 2Wiki. Hub downweighting $p=0.5$.
- **Environment**: CPU-only, 4 GB RAM budget. SpaCy NER (`en_core_web_sm`) or regex. Dense retrieval uses HNSW (M=32, efConstruction=200, efSearch=64).

| **GraphDense** | **0.782** | **0.844** | **0.968** | **0.875** | 582.7 |

**Table 2: 2WikiMultiHopQA validation results (10,000 queries)**
| Method | R@5 | R@10 | Hit@10 | MRR | QTime (s) |
|---|---|---|---|---|---|
| BM25 | 0.579 | 0.643 | 0.972 | 0.819 | 303.1 |
| Dense | 0.579 | 0.609 | 0.930 | 0.885 | 86.0 |

*Key Finding*: GraphDense is competitive and slightly higher than GraphHybrid in R@10 on both datasets. RRF remains a strong hybrid baseline, while BM25+CE delivers strong MRR at higher latency.

## 6. Ablations

**Table 4: Effect of lightweight enhancements on full validation (GraphHybrid)**
| Variant | Hotpot R@10 | Hotpot QTime (s) | 2Wiki R@10 | 2Wiki QTime (s) |
|---|---|---|---|---|
| Base | 0.775 | 485.3 | 0.743 | 367.9 |
| **+ALL** (EL+PRUNE+MIX) | **0.773** | **350.5** (-28%) | **0.743** | **308.5** (-16%) |

*Key Finding*: Hub pruning and explicit seed mixing reduce query time substantially (16–28%) with negligible Recall@10 changes.

**Table 5: RRF variants and graph hybrids**
- **GraphRRF** (RRF-seeded PPR) further improves Recall@10 over standard RRF (HotpotQA: 0.851 → 0.867; 2Wiki: 0.697 → 0.794), showing that stronger seeds plus traversal yield additional gains.

## 7. Efficiency and Scalability
- **Indexing**: Scales roughly linearly with corpus size (consistent with linear-time graph construction).
- **Query Time**: Grows with graph density and PPR iterations. Graph variants relying on external seeding (GraphHybrid/GraphRRF) are the most expensive among graph methods, while the cross-encoder reranker is the most expensive overall.
- **Memory**: All methods operate well within the 4 GB RSS limit (e.g., GraphDense query RSS ~427 MB on HotpotQA).

---

## 8. Discussion
- Graph-based retrieval recovers multi-hop evidence beyond lexical matching, but performance is sensitive to seed quality and graph noise.
- The TF–IDF graph baseline performs poorly relative to entity graphs, suggesting that explicit entity co-occurrence provides a more effective topology for multi-hop navigation than term-level edges.
- RM3 underperforms BM25 on these datasets, suggesting classic PRF is not consistently reliable for multi-hop retrieval.

---

## 9. Limitations
1. Evaluated on two multi-hop QA datasets; end-to-end QA uses a small extractive model (DistilBERT).
2. No full entity linking or coreference resolution; title-alias disambiguation is intentionally minimal.
3. Approximate dense indexing (HNSW) trades recall for speed; default settings can underperform exact seeding.
4. Hyperparameters tuned on validation subsets may introduce mild overfitting (mitigated by robustness checks in Appendix Table A.15).
5. Does not re-implement training-heavy baselines (e.g., MDR) under identical CPU-only constraints.

---

## 10. Conclusion
We present a CPU-only, linear-time GraphRAG pipeline (SPRIG) that avoids LLM-based graph construction while improving multi-hop retrieval quality. Simple co-occurrence graphs plus PPR provide a practical and reproducible path toward democratizing GraphRAG. Lightweight title-alias disambiguation and hub pruning reduce query-time costs by 16–28% with negligible Recall@10 changes, providing an actionable efficiency knob for CPU deployments. Code and scripts will be released.
